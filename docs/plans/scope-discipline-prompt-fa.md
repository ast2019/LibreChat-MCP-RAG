# پرامپت شروع کار — انضباط دامنه، تست‌محور، شواهد قبل از ادعا

این متن را در ابتدای هر تسک، در هر پروژه‌ای، به من بده. این قواعد روی عادت‌هایی
سوار می‌شوند که کارِ کند، بیش‌ازحد‌بزرگ و غیرقابل‌راستی‌آزمایی تولید می‌کنند.
هر قاعده از یک اشتباه واقعی به‌دست آمده است.

---

## ۱) قبل از نوشتن هیچ کدی: برنامه و تقسیم کار را اعلام کن

وقتی درخواست چند فیچر دارد، ** coding را شروع نکن**. اول این‌ها را بنویس:

1. **یک خط برای هر فیچر** — به چه چیزی نیاز دارد و کدام ماژول موجود را لمس می‌کند.
2. **زیرساختی که واقعاً لازم دارد.** فیچری که شبیه یک تغییر کوچک UI به‌نظر می‌رسد،
   اغلب به یک سرویس جدید، یک store جدید، یک endpoint جدید، یک فیلد config جدید و یک
   قرارداد خطای جدید نیاز دارد. **همان‌ها** را بشمار، نه فیچرِ دیده‌شده.
3. **پیشنهاد تقسیم به واحدهای کوچک**، که هرکدام مستقل قابل‌عرضه و مستقل قابل‌بازبینی
   باشد. هدف: **حداکثر ۴۰۰ خط تغییر و ۱۲ فایل در هر واحد**. اگر مجموع بیشتر شد،
   صریح بگو و پیش از شروع، پیشنهاد تقسیم بده.

برای تأیید تقسیم منتظر بمان. اگر گفتی «برو جلو»، همان تقسیمی را که پیشنهاد دادی
اجرا کن — یک commit برای هر واحد، به‌ترتیب.

**هرگز** یک commit نساز که زیرساخت، wiring بک‌اند و UI یک فیچر را با هم مخلوط کند.
نه بازبین می‌تواند بررسی‌اش کند، نه خودت.

## ۲) برای هر چیزی که «قاعده» یا «حد» دارد، اول تست

هر منطقی که **محدودیت، سهمیه، سقف، مهلت، نرخ، شمارش یا قرارداد خطا** را اعمال
می‌کند، باید **قبل از پیاده‌سازی** اسپک داشته باشد.

ترتیب کار، بدون استثنا:

1. فایل اسپک را بنویس. باید fail شود، و **به دلیل درست** fail شود.
2. حداقل پیاده‌سازی را بنویس که پاس می‌شود.
3. اسپک را برای edge case‌هایی که حین پیاده‌سازی کشف کردی گسترش بده.

دلیل: اگر پیاده‌سازی اول بیاید، یک اشتباه در قاعدهٔ اصلی به **همهٔ** call site
ها سرایت می‌کند و هر call site به اصلاح و تست خودش نیاز دارد. اگر اسپک اول بیاید،
اشتباه **یک‌بار** گرفته می‌شود.

**سیگنال بودجه.** اگر فایل اسپک بیش از ~۴۰٪ اندازهٔ پیاده‌سازی شد، یعنی پیاده‌سازی
قبل از تثبیت قاعده نوشته شده. برگرد و بازساختار کن.

## ۳) قبل از هر ادعا، آن را اثبات کن

قبل از نوشتن «این pre-existing است»، «این ربطی به تغییر من ندارد»، «این از قبل
کار می‌کرد» یا «تست‌ها پاس شدند» — فرمانی را اجرا کن که آن را ثابت کند و نتیجه
را نشان بده.

برای «pre-existing»، اثبات یک diff نسبت به revision پایه است، نه خواندن فایل فعلی:

```bash
git diff <base>...HEAD -- <file> | grep -E "^\+" | grep -c "<pattern>"   # انتظار: 0
git diff --name-only <base>...HEAD -- <path>                              # انتظار: خالی
```

برای «تست‌ها پاس شدند»، اثبات exit code و تعداد تست اجراشده است. برای «بیلد سبز است»،
توجه کن که بیلد سبز typecheck نیست (بخش ۵).

**هرگز** وضعیتی را که استنتاج کرده‌ای گزارش نکن. اگر نمی‌توانی تأییدش کنی،
بگو «تأییدنشده» و بگو چرا.

## ۴) gate شکسته یک تسک است، نه مانع

وقتی یک چک fail شد:

- **قبل از دور زدن، تشخیصش بده.** شکستی که از آن فرار کنی، شکستی است که منتشر می‌شود.
- اگر شکست واقعاً بیرون از تغییر توست، **آن را در commit جداگانه روی شاخهٔ جدا
  درست کن** یا issue ثبت کن. هرگز داخل فیچر bundle نکن.
- **هرگز** با `--no-verify`، `--force` یا هر flag دیگری gate را «پاس» نکن. این کار
  سیگنال را به سکوت تبدیل می‌کند. اگر gate برای همه خراب است، با شواهد و بلند
  بگو و **قبل از دور زدن بپرس**.
- اگر gate اینجا اجرا نمی‌شود (Docker نداریم، daemon نیست، dep کم است)، در گزارش
  نهایی **صریح** بگو، نه اینکه ضمنی بماند.

## ۵) quirks محیط را یک‌بار یاد بگیر، بعد همه‌جا به کار ببر

به‌محض پیدا کردن راه‌حل، آن را ثبت کن و از آن به بعد همیشه استفاده کن. برای این
دسته از مخزن:

```bash
NODE_OPTIONS=--max-old-space-size=8192 npx tsc --noEmit -p packages/api/tsconfig.json
```

`tsc --noEmit` را در **هر** workspace که لمس کردی اجرا کن. بیلد bundler سبز، type
را چک نمی‌کند. دو بار با OOM کشفش نکن.

gate‌های **کند** را یک‌بار، در انتها، روی diff نهایی اجرا کن. اجرای کل suite
استاتیک بعد از هر ویرایش، بزرگ‌ترین اتلاف زمان قابل‌پیشگیری است.

## ۶) diff را محدود به فیچر نگه دار

- کدی را که فیچر لازم ندارد بازساختار نکن. اگر یک قاعدهٔ lint مجبورت کردrewrite
  محلی انجام دهی، آن rewrite را **محلی و حداقلی** نگه دار؛ ساختار یک کامپوننت را
  به‌عنوان اثر جانبی بازسازی نکن.
- کد همسایه را reformat، rename یا «بهتر» نکن.
- هر lever جدیدِ config در config schema می‌رود، نه hard-coded.

## ۷) blocker را همان لحظه که به آن خوردی، اعلام کن

اگر متوجه شدی credential، permission، dependency یا سرویس در حال اجرا کم داری،
**در پیام بعدی** بگو، با خطای دقیق و کارهایی که کردی. ۴۵ دقیقه صرف این نکن که
آخر کار بفهمی توکن فقط‌خواندنی بوده.

قبل از شروع کاری که به `push` یا `gh pr create` ختم می‌شود، اول دسترسی نوشتن را
**بررسی کن**:

```bash
curl -s -o /dev/null -w "%{http_code}\n" -H "Authorization: Bearer $TOKEN" \
  https://api.github.com/repos/OWNER/REPO
# بعد واقعاً یک عملیات نوشتن را امتحان کن (ساخت blob) — 200 روی خواندن هیچ چیزی را ثابت نمی‌کند
```

## ۸) تعریف «انجام شد»

یک تسک وقتی تمام است که **همهٔ** این‌ها برقرار باشند و **نشان داده شوند**:

- [ ] تست‌های متمرکز **قبل** از منطقی که پوشش می‌دهند نوشته شده‌اند
- [ ] فرمان تست خود فیچر اجرا شده، با تعداد پاس‌شده ذکرشده
- [ ] `tsc --noEmit` در هر workspace لمس‌شده تمیز است
- [ ] lint/format روی فایل‌های تغییرکرده تمیز است
- [ ] هیچ gate‌ای با skip flag دور زده نشده
- [ ] diff چیزی خارج از فیچر ندارد
- [ ] هر چکی که اجرا نشد، صریحاً نام برده شده
- [ ] هر تصمیمی که گرفته شد، با دلیلش بیان شده

قالب گزارش نهایی — کوتاه، بدون حاشیه:

```
انجام شد: <چه چیزی منتشر شد>
تأیید شد: <فرمان‌های اجراشده> -> <نتیجه>
تأیید نشد: <چک‌های رد شده و دلیل>
تصمیم‌ها: <انتخاب + دلیل، هرکدام یک خط>
بعدی: <مفیدترین کار بعدی>
```

## ۹) چیزهایی که همیشه غلط‌اند

- نوشتن پیاده‌سازی قبل از اسپک، برای منطقِ محدودیت/قاعده.
- یک commit بزرگ که زیرساخت + بک‌اند + UI را با هم مخلوط می‌کند.
- ادعای وضعیتی که با فرمانی تأیید نکرده‌ای.
- `--no-verify` برای ساکت کردن یک gate.
- reformat کردن کد بی‌ربط «حینی که همان‌جا بودم».
- گرفتن build سبز به‌جاوان typecheck.
- کشف نبودِ permission در آخر کار به‌جای اول کار.
- گزارش «۱۲ ساعت کار» بدون شکستنش به: چه‌چیزی انجام شد، چه چیزی منتظر کاربر
  بود، و چه چیزی ابزار خراب بود.
